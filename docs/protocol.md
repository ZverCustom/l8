# ZVER L8 JSON API v1 — проект контракта

Редакция проекта: 23.11.2026. **API v1 целиком ещё не реализован.**
Промежуточная реализация P1-A (с `44b99ae`): `GET /api/info`, USB `{"cmd":"info"}`
и `channels[i].reason` в legacy-status. P1-B: `savedRevision` и `bootId` в legacy-status,
`savedRevision` в ответах legacy preview/apply/save/discard/touch (HTTP и USB),
возможность `config.savedRevision`. Конверт команд, preview v1 и SSE v1 — P1-C.
Документ задаёт результат P1 из [плана приложения](development/app-plan.md).
Изменения проекта обсуждаются в отчёте/ревью до публикации совместимого API v1.

## 1. Версии и обнаружение

`GET /api/info` возвращает объект информации. Та же информация доступна как
`result` команды `info` по HTTP и USB. Пример будущего ответа:

```json
{
  "product": "ZVER L8",
  "hardware": 3,
  "deviceId": "L8-001122AABBCC",
  "bootId": "00112233445566778899aabbccddeeff",
  "firmware": "0.4.0+example",
  "protocol": {"major": 1, "minor": 0},
  "configSchema": 5,
  "transports": ["http", "usb"],
  "capabilities": ["info.v1", "commands.v1", "channel.reason", "config.savedRevision", "preview.v1", "status.sse", "ota.http"],
  "limits": {
    "channels": 8,
    "maxCommandBytes": 24576,
    "maxConfigBytes": 24000,
    "maxLedCount": 1000,
    "maxChannelAmps": 5,
    "previewLeaseMs": 60000,
    "previewIntervalMs": 100,
    "statusIntervalMs": 500,
    "maxSseClients": 3
  }
}
```

Значения модели/памяти/лимитов берутся из прошивки, capabilities перечисляют только
реализованные функции. `info.v1` означает только наличие этого объекта обнаружения
(`/api/info`, USB `info`) и **не означает** поддержку конверта команд v1 — для него
отдельная возможность `commands.v1`. Сборка P1-A объявляет ровно
`["info.v1", "channel.reason", "ota.http"]`, P1-B добавляет `config.savedRevision`; `commands.v1`, `config.savedRevision`,
`preview.v1` и `status.sse` появятся вместе с соответствующими частями P1-B/P1-C.
В P1-A `limits.maxCommandBytes` = 24000 (фактический предел текущих HTTP/USB-обработчиков);
24576 вводится с конвертом v1. Прошивки до `44b99ae` возвращают 404 на `/api/info`.

- `deviceId` — стабильный непрозрачный ID платы, производный от заводского ID чипа;
  не меняется при обычной прошивке или очистке пользовательских настроек, не является паролем.
- `bootId` — новый случайный 128-битный идентификатор при каждой загрузке, 32 hex-символа.
- `protocol.major` меняется при несовместимом контракте; minor — при совместимых добавлениях.
- `configSchema` независим от версии API и firmware. В P1 остаётся 5.
- Клиент игнорирует неизвестные дополнительные поля. Неизвестный reason отображает
  нейтрально, не интерпретирует как разрешение выхода. Неизвестная обязательная
  возможность отключает соответствующий элемент управления.
- При 404 старой прошивки клиент предлагает обновление или явно реализованный legacy-режим;
  не предполагает наличие API v1 по строке версии firmware.

## 2. Одинаковое сообщение для HTTP и USB

Новый HTTP-маршрут: `POST /api/command`, `Content-Type: application/json`.
USB: тот же UTF-8 JSON одной строкой с завершающим `\n`.

```json
{"v":1,"id":"req-27","cmd":"preview","bootId":"00112233445566778899aabbccddeeff","client":"editor-01","revision":42,"strip":1,"patch":{"color":255,"brightness":35}}
```

Успех:

```json
{"v":1,"id":"req-27","bootId":"00112233445566778899aabbccddeeff","ok":true,"revision":43,"savedRevision":40,"result":{"master":true,"previewActive":true,"previewRemainingMs":60000}}
```

Ошибка:

```json
{"v":1,"id":"req-28","bootId":"00112233445566778899aabbccddeeff","ok":false,"revision":43,"savedRevision":40,"error":{"code":"REVISION_CONFLICT","message":"Configuration changed"}}
```

HTTP отдаёт этот объект в теле ответа. В USB он имеет прежний префикс `L8 `
и заканчивается переводом строки. Остальные строки USB — диагностический текст,
клиент не пытается разобрать их как ответы. Поле `id` сопоставляет запрос и ответ.
Префикс, HTTP-заголовки и будущая BLE-фрагментация не входят в JSON-контракт.

- `v` обязателен и равен 1; отсутствие `v` допускается только у legacy-команд.
- `id` и `client` — ASCII-строки длиной 1–48 байт. `client` постоянен для сессии редактора.
- Для всех команд изменения нужен актуальный `bootId`; после перезагрузки старые
  команды отклоняются, даже если числовая revision снова совпала.
- Revision — uint32, рассматривается как непрозрачный токен внутри bootId.
  Клиент сравнивает равенство, не вычисляет «количество пропущенных изменений».
- Boolean и числа проверяются по типу. `"true"`, NaN, бесконечности и неизвестные
  поля команды изменения отклоняются, а не неявно преобразуются.
- HTTP и USB используют один dispatcher, который возвращает один тип result/error;
  транспорт добавляет framing/auth и выбирает HTTP-код.

## 3. Команды P1

В таблице указаны поля сверх общего конверта. Индексы каналов **0…7**,
интерфейс показывает человеку **1…8**, порядок соответствует силовым контактам v3.

| cmd | Дополнительные поля | Результат / действие |
|---|---|---|
| `info` | нет | Информация из раздела 1 |
| `status` | нет | Текущий status, включая reason и savedRevision |
| `get_config` | `view`: `baseline` по умолчанию или `effective`; для effective — client | Конфигурация и указание view; password скрыт, keepPassword=true |
| `preview` | client, revision, strip, patch | Малый патч color / brightness / speed в RAM |
| `apply` | client, revision, config | Полная проверенная конфигурация в RAM |
| `save` | client, revision | Зафиксировать preview во flash, ответ после подтверждения записи |
| `discard` | client, revision | Отменить preview, сохранить runtime Master |
| `touch` | client, revision | Продлить аренду существующего preview |
| `action` | action и поля из следующей таблицы | Управление / служебное действие |

`get_config` с view=baseline возвращает конфигурацию до активного preview, которая
может ещё ожидать отложенной записи; это не синоним «прочитано с диска».
View=effective во время preview доступен его владельцу и нужен для восстановления
после неоднозначного ответа. Чужому редактору возвращается EDITOR_BUSY.
Без preview оба view совпадают. Секретный backup остаётся отдельным авторизованным
HTTP-маршрутом; экспорт паролей по всем транспортам не вводится в P1.

| action | Поля | Условия |
|---|---|---|
| `master` | on:boolean | Задаёт состояние, не toggle; не отменяет блокировки питания |
| `reset` | channel:-1…7 | Сброс всех / одного канала, только при Master OFF |
| `preset_save`, `preset_load` | slot:0…2, client, revision | Без чужого/активного preview; сохраняют Master |
| `calibrate` | client, revision | Без preview, доступный IMU; изменяет конфигурацию |
| `reconnect` | нет | Без preview, явно запускает подключение к сохранённой сети |
| `reboot` | нет | Master OFF, выходы заблокированы; preview не сохраняется |

Команды изменения конфигурации проверяют revision. Master/reset/reconnect/reboot
не требуют конфигурационной revision, но требуют bootId. Во время OTA изменения
заблокированы одинаково на HTTP и USB; чтение остаётся доступным в пределах работы сервера.
Изменение Master не увеличивает конфигурационную revision. `touch` и чтение тоже.
Результат `master:on` подтверждает команду, а не наличие 12 В или физически горящую ленту.

## 4. Ревизии и достоверное сохранение

Status и ответы команд содержат `revision` / `savedRevision`; legacy-status сохраняет
имя `configRevision` и добавляет `savedRevision` и `bootId`. Их значения согласованы
с конвертом команды status. `savedRevision` может быть null, если подтверждённой
сохранённой конфигурации ещё нет.

`savedRevision` обозначает ревизию конфигурации, содержимое которой подтверждено
в устойчивом хранилище. Это не номер запроса Save и не время последнего вызова файловой функции.
Счётчики живут в текущей загрузке, сохранять их в schema 5 не требуется.

| Ситуация | Требуемое поведение |
|---|---|
| Загрузили корректный schema 5 из основного файла или проверенного backup | Загруженная revision считается сохранённой |
| Defaults без файла, неподтверждённая миграция | Не показывать «Записано» до успешной записи |
| Изменили конфигурацию / preview | Новая revision, savedRevision остаётся прежней |
| Запланировали запись на 1,5 с | Снимок хранит собственную revision |
| Старый снимок записался при более новом preview | savedRevision относится к старому снимку; новая RAM-конфигурация не объявляется сохранённой |
| Успешный save preview | После установки файла savedRevision соответствует возвращаемой revision |
| Ошибка записи / rename | Не продвигать savedRevision; preview доступен для явного повтора/отмены |
| Отмена или истечение preview | Создать новую revision возврата; дальнейшее правило ниже |

При возврате к baseline, содержимое которого уже подтверждено во flash,
новая revision может стать savedRevision **без лишней физической записи**:
это новый токен того же подтверждённого содержимого. Если baseline ещё ожидает
записи, возврат не делает его сохранённым; pending-снимок должен быть связан с
новой revision возврата. Связь доказывается идентичностью снимка/содержимого,
а не предположением «раз отменили, значит всё сохранено».

Во время неудачного commit сохранить прежний pending-снимок и его revision.
Нельзя автоматически записать неудачный preview вместо него. Flush сам по себе
не создаёт новую RAM-конфигурацию. Все пути пресетов/калибровки/legacy-save участвуют
в том же учёте. Реализация проверяется тестами настоящего settings.cpp.

### Реализация P1-B

- **Содержимое** — каноническая сериализация RAM-конфигурации schema 5 (тот же
  кодировщик, что пишет файл, вместе с паролем; runtime Master в неё не входит).
  Идентичность снимков проверяется 64-битным хешем FNV-1a этой строки.
- Прошивка хранит три привязки: *подтверждённое* содержимое и его последний токен,
  *pending*-снимок и его токен, *baseline* активного preview и токен до preview.
- Новый токен вне preview сверяется по содержимому: совпал с pending — pending
  переназначается на него; совпал с подтверждённым — он становится savedRevision
  без записи. Токены, созданные во время preview, никогда не объявляются сохранёнными,
  даже если патч вернул прежние значения.
- Запись снимка: успех — подтверждённым становится содержимое снимка и его токен;
  если RAM вне preview совпадает с ним, savedRevision = текущей revision.
  Запись, во время которой активен более новый preview, оставляет текущую revision грязной.
- `settingsSave()` во время preview снимает baseline и связывает его с токеном до preview.
  Сохранение содержимого, уже подтверждённого во flash, не пишет файл повторно.
- Порядок установки сохраняет одну проверенную копию на каждом шаге: основной файл
  переносится в backup только пока он и есть подтверждённая копия; иначе подтверждённой
  копией остаётся backup, а устаревший или повреждённый основной файл удаляется.
  Повторные отказы установки больше не удаляют единственный уцелевший backup.
- После отказа маркер сбрасывается в null, только если на FS не осталось ни основного
  файла, ни backup. Загрузка из основного файла или backup schema 5 подтверждает
  содержимое; миграция schema 3/4 подтверждается только после успешной записи schema 5.
- Счётчики и маркер живут в RAM текущей загрузки, в файл не пишутся; связь с
  загрузкой задаёт `bootId` (в legacy-status тоже).

UI показывает «Записано» только при отсутствии локальных неотправленных изменений,
неоднозначной операции и активного preview, когда revision == savedRevision.
Неравенство или null означает «Применено, не сохранено». Отправляемые изменения
имеют отдельное состояние. Открытая чистая страница не пишет defaults автоматически.

## 5. Предпросмотр и один запрос в работе

Аренда редактора глобальна для всех транспортов: USB и HTTP не могут одновременно
владеть разными preview. Срок 60 с, heartbeat примерно раз в 10 с. Ответы и status
сообщают previewActive, previewOwner и оставшееся время; client — идентификатор,
не механизм авторизации. Сервер сам восстанавливает baseline при истечении аренды.

Клиентский отправитель:

1. При движении хранит последние значения по паре канал/поле.
2. Начинает передачу примерно раз в 100 мс; один запрос изменения в полёте.
3. Во время запроса обновляет ожидающие значения, не создаёт очередь старых патчей.
4. После ответа отправляет актуальный остаток с новой revision.
5. Change/pointerup помечает финальное значение обязательным; оно не теряется,
   даже если предыдущий запрос ещё не завершён.
6. Save сначала завершает финальный preview, затем сохраняет подтверждённую revision.
   Изменения, сделанные во время Save, остаются новым несохранённым preview.
7. 409 или неоднозначный обрыв останавливает отправку до сверки с устройством.

Один запрос в полёте — правило клиента, не ожидание, что WebServer бесконечно
буферизует очередь. SSE не считается запросом изменения. Сервер проверяет
bootId, revision, владельца и все ограничения на каждом запросе независимо от клиента.

## 6. Причина состояния канала

`channels[i].reason` формируется задачей power вместе с её snapshot, после обработки
измерений/ошибок текущего цикла. UI переводит код, не выводит причину из своих
копий настроек. Выбор при одновременных условиях — первый подходящий по таблице:

| Приоритет | reason | Условие |
|---|---|---|
| 1 | `io` | Состояние ключей не подтверждено из-за I/O; нельзя объявлять физическое отключение достоверным |
| 2 | `fault` | Защёлкнутая неисправность без ожидающего автоматического повтора |
| 3 | `inhibit` | Самопроверка, OTA, reboot или другая общая блокировка выходов |
| 4 | `novbat` | Напряжение вне допустимого диапазона, включая питание только USB |
| 5 | `ign` | Общая политика требует IGN, но его нет |
| 6 | `master` | Runtime Master выключен |
| 7 | `disabled` | Канал запрещён в конфигурации |
| 8 | `engine` | Уже существующая общая настройка отключила питание из-за состояния двигателя/данных |
| 9 | `retry` | Ожидание конечного автоповтора при остальных выполненных разрешениях |
| 10 | `on` | Выход включён, подтверждён и не заблокирован |

Поле не заменяет fault, retryPending, retryInMs, brightnessScale и ioOk/ioFault.
При retryPending и отсутствии питания reason=novbat, а отдельные поля показывают
ожидающий повтор. Мягкое ограничение яркости не является причиной выключения.
`engine` описывает существующее поведение, а не вводит новую поканальную политику.
До первого цикла задачи power snapshot содержит `io`. Если все разрешения выполнены,
а канал выключен, возвращается диагностический `fault` (срабатывание защиты в этом же
цикле); это не отдельное обнаружение аппаратной неисправности.
UI сначала переводит `reason`, а fault/retry/ограничение яркости показывает только
как детализацию; таблицу приоритетов в UI не повторяет. Legacy `powerStatus`
остаётся общей сводкой и не определяет состояние отдельных каналов.
Новый reason не должен изменять физические условия управления ключом.

## 7. HTTP, USB, SSE и ошибки

- HTTP-команды изменения требуют действующий `X-L8-Token` из `/api/session`.
  Токен локальной сессии защищает от случайных cross-origin запросов, но не является
  паролем устройства. USB в P1 предполагает физический доступ и не использует HTTP-заголовок.
- Старый HTTP API и USB без v остаются совместимыми адаптерами. Их payload не
  заменяется новым конвертом без версии. Новое приложение использует v1.
- Максимум 24576 UTF-8 байт на команду, без `L8 ` и перевода строки; config до 24000 байт.
  На USB превышение сбрасывается целиком до следующего newline, хвост команды не исполняется.
  Legacy-команды сохраняют прежний предел 24000 байт, даже если новый буфер больше.
- Ошибка JSON/конверта возвращает id=null, если id нельзя достоверно извлечь.
- HTTP SSE: `/api/events?v=1&token=…`, event=`status`, данные
  `{v:1, bootId, seq, revision, savedRevision, status:{…}}` в корректном JSON.
  Без v остаётся прежний payload встроенного UI. Полный снимок каждые 500 мс,
  максимум три клиента, медленный клиент отключается через 2 с.
- В P1 USB использует команды status без обязательного unsolicited-потока.
  Для будущего USB/BLE push требуется отдельная capability; не обещать её заранее.
- Обрыв SSE сразу отражается как потеря потока, без затирания локального черновика.
  Полная потеря связи уточняется контрольным чтением; восстановление требует info/status
  и проверки bootId. Возврат HTTP ещё не доказывает, что предыдущая запись не выполнилась.

| error.code | HTTP | Смысл |
|---|---|---|
| BAD_JSON / INVALID_ARGUMENT / UNSUPPORTED_VERSION | 400 | Некорректное сообщение/тип/версия |
| AUTH_REQUIRED | 403 | Нет действующей HTTP-сессии |
| UNKNOWN_COMMAND | 404 | Команда неизвестна |
| BOOT_CHANGED / REVISION_CONFLICT / EDITOR_BUSY / PREVIEW_EXPIRED | 409 | Требуется сверка состояния редактора |
| BUSY / OUTPUT_BLOCKED / MASTER_MUST_BE_OFF | 409 | Действие сейчас недоступно |
| FRAME_TOO_LARGE | 413 | Превышен размер сообщения |
| UNSUPPORTED_CAPABILITY | 501 | Функция не реализована |
| FLASH_WRITE_FAILED | 507 | Запись не подтверждена |
| INTERNAL_ERROR | 500 | Прочая внутренняя ошибка |

Клиент принимает решения по code, а не по английскому message. `id` служит
корреляции: сервер v1 **не обещает exactly-once или дедупликацию** по id.
Чтения можно повторять. После потери ответа на изменение сверить bootId,
revision, savedRevision и при необходимости effective-конфигурацию, затем принять
явное решение. Повторное получение HTTP-токена не разрешает повторять неоднозначную запись.

## 8. OTA и будущие транспорты

В P1 OTA остаётся HTTP multipart `/api/ota`, отдельным от JSON-команд; сохраняются
блокировки, выключение выходов и подтверждение новой прошивки после самопроверки.
USB-загрузка через ROM bootloader/esptool — отдельный будущий механизм восстановления,
а не команда, которую обязана выполнять неисправная основная прошивка.

BLE пока не объявляется. Его транспорт должен переносить те же сообщения с
согласованными фрагментацией, лимитом сборки, порядком, тайм-аутами и обратным давлением.
До реализации измеряются внутренний heap/буферы, flash и совместная работа с Wi-Fi.
PSRAM не заменяет все потребности BLE во внутренней памяти. В текущей таблице
разделов app0/app1 по `0x640000` (6,25 МиБ); образ около 950 КБ не равен пределу OTA-раздела.

Первый Flutter-прототип проверяется на реальных Android/iOS с Wi-Fi AP без интернета
и включённой мобильной сетью, при уходе в фон и возврате. Не считать результаты
эмулятора подтверждением маршрутизации и разрешений реального телефона.
