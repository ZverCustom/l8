# L8 0.3.4-dev: ограничение паузы AP по активности HTTP

Продолжение ревью `29bfd13`. На плату не записано, аппаратные проверки отложены
до подключения пользователем. Версия остаётся 0.3.4-dev; сборку отличает SHA256.

## Поведение

- Подключённый к AP телефон без HTTP-запросов не блокирует STA-повторы.
  Окно активности — 60 секунд после последнего запроса к странице `/` или
  зарегистрированным `/api/*` через AP. Учитываются также части OTA-upload.
- Окно продлевается только для соединений с localIP, равным IP точки доступа.
  HTTP через STA и USB-команды его не продлевают.
- При активном окне новые фоновые попытки приостановлены; после его истечения
  действует обычный backoff 30 с с AP / 10 с без AP. Идущая ассоциация/DHCP
  продолжается по своим прежним дедлайнам.
- После успешного STA AP закрывается, когда истекает то же окно, даже если телефон
  остался ассоциирован. Видимая вкладка с опросом считается активным интерфейсом;
  в скрытой вкладке опрос приостановлен и возобновляется при возвращении.
- Если DISCONNECTED потерян, Online сверяется с WL_CONNECTED и STA_CONNECTED_BIT.
  При отсутствии обоих автомат переходит в Failed; срок следующего повтора
  не сдвигается на каждом проходе. При сохранённой ассоциации ожидается DHCP.
- Потери событий очереди теперь считаются атомарно и выводятся из основного цикла.
  Callback по-прежнему не пишет в лог. В status.wifi добавлены apHttpActive
  и droppedEvents; apClients остаётся диагностикой, но не определяет паузу.

## Диагностические файлы

По умолчанию `capture_wifi_boot.py` создаёт уникальный UTC-файл в `L8/logs/`,
с правами 0600; отсутствующие каталоги создаются. Пример явного пути:
`--output logs/wifi-boot-0.3.4.log`. Каталог logs исключён из Git.
Образ исходной логики 0.3.3 с ранними событиями перенесён из /tmp в
`logs/diagnostics/l8-0.3.3-wifi-early-log.bin`. Рядом приватный JSON с базовым
коммитом, назначением, размером и SHA256. Контрольная сумма после переноса совпала:
`6311ce30cfb0981f06d933c798872327b4eff83247924a1e149c48f02b14d1be`.
Бинарник может содержать Wi-Fi credentials, поэтому в Git не включён.

## Открытые аппаратные проверки

- Причина первой неудачной попытки Wi-Fi по-прежнему не установлена.
- Снять ранние логи исходной 0.3.3 и подготовленной 0.3.4. Отдельно проверить
  последовательность первого non-ASSOC_LEAVE, внутреннего повтора ядра и возможного
  дополнительного reason 8. Текущее поведение для этого reason не менялось:
  если он сопровождает внутренний повтор, возможен лишний begin через 10 с.
  Исправление по предположению без аппаратного лога не заявляется.
- AP с телефоном при недоступной домашней сети: серия сохранений; затем скрыть
  вкладку и оставить телефон ассоциированным более 60 с. Проверить возобновление
  попыток и погашение AP после успеха STA. Наблюдать через USB: запросы /api/status
  через AP сами обновляют окно активности. Проверить, что запросы через STA
  не удерживают AP, а видимая вкладка через AP удерживает.
- Медленные ассоциация/DHCP и ошибочный/прерванный OTA до/после boot-confirm —
  аппаратные проверки из предыдущего отчёта также остаются открытыми.

Офлайн-тесты не выданы за испытания радио, HTTP на ESP32 или непрерывности питания.
